Executive summary

The Tax Ombud Operations Platform is an integrated CRM + ERP + ITSM (Information Technology Service Management) system built for the Office of the Tax Ombud (OTO) of the Federal Republic of Nigeria. It serves three audiences from a single backend through three distinct front-ends:
The public — Nigerian taxpayers lodging and tracking complaints against tax authorities.
OTO staff — case officers, supervisors, approvers, executives, and corporate-services staff who triage, investigate, and resolve those complaints, and who run OTO's internal HR, payroll, IT, and procurement operations.
OTO administrators — sitewide configuration, role governance, integrations, audit, super-admin controls.
The Platform's core job is to receive, manage, route, escalate, approve, and resolve complaints against tax authorities (NRS, NCS, state IRS, LGRC, NPA, AMCON, NSC, and others), then forward them to the appropriate handling authority while preserving an unbroken audit trail. Around that core, it provides the full operational fabric an independent government office needs to run: HR, payroll, leave, attendance, performance, internal tickets, projects, inventory, secured document filing with OCR, e-voting, e-signatures, omnichannel taxpayer communication, knowledge management, automation/workflow rules, and reporting.
Scale of the build:
19 functional sections, 119 topics (modules/pages), 205 distinct permission grants
Three front-end experiences (public portal, taxpayer portal, staff studio) sharing one backend
Multi-stage configurable workflow with 5 confirmed officer queues (Receiving → Verifier → Assessment → Investigation/Resolution → 1st Level Approval → 2nd Level Approval)
Multi-channel omnichannel inbox (Chat, Email, Calls, SMS, WhatsApp, Facebook, Instagram, Telegram, X/Twitter)
Audit-grade governance including admin impersonation with full traceability
NDPR-aligned data handling for Nigerian PII (NIN, BVN, taxpayer financial data)
Primary success metrics for the build:
Median complaint intake-to-acknowledgement time ≤ 1 business day
≥ 70% of complaints resolved at Assessment Officer (B1) stage without further escalation [ASSUMPTION: KB suggests "Typically 70–80% of cases should resolve at B1"]
100% of state transitions audited and recoverable
99.5% uptime for the public portal lodging flow [ASSUMPTION: standard gov SLO]
Zero PII leakage incidents
Non-negotiable foundational principle (see §2.3): The Platform is self-administered from the UI by the Super Admin role. Every operational adjustment — new departments, new service domains, new roles, new permission grants, new email templates, new feature toggles, new integration credentials,

new custom entity fields, branding changes, cache flushes, session revocations — is performed in the
staff studio UI with no console access, no	edits, no database surgery, and no code redeploy.
This is the single most consequential architectural constraint in this PRD and shapes the stack choice, schema design, and module boundaries.



Product context and goals


Who OTO is, who they serve, what hurts today
The Office of the Tax Ombud is constituted as an impartial mediator between Nigerian taxpayers and tax authorities. Its tagline on the public portal is "An Independent Office for Fair and Transparent Tax Administration." When a taxpayer (individual, SME, or large corporation) has a grievance against a tax authority — disputed assessment, unresolved VAT remittance, alleged poor service at an MSTO office,
refusal to process refunds, etc. — OTO is the recourse channel.
Today, without a system like the Platform, OTO faces these operational problems:
Fragmented intake: complaints arrive by email, phone, social media, in-person visits, and physical letters. No single record.
Untraceable handoffs: cases move between officers and departments without an audit trail.
No SLA enforcement: a taxpayer's complaint can sit untouched for weeks.
Manual forwarding to authorities: officers manually email/letter the NRS/NCS/etc. with no status sync.
No reporting: leadership cannot answer "how many VAT-related complaints did we receive this quarter, and how many did we resolve at Assessment vs. escalation?"
Internal operations on spreadsheets: HR, payroll, leave, IT tickets, procurement all run on disconnected tools.
The Platform solves these by giving OTO a single system covering both the outward-facing complaint mediation function and the inward-facing organisational operations (HR/Payroll/IT/Finance/Procurement) needed to run an independent statutory office.

Strategic product goals


Foundational principle — the Platform is self-administered from the UI
This is a non-negotiable architectural constraint that shapes every other decision in this PRD.
The live system being cloned was deliberately built so that a Super Admin user, signed into the staff studio, can manage and administer every aspect of the application from the UI alone. There is no scenario in normal operations where an administrator must SSH into a server, edit a configuration file, run a database migration, redeploy code, or call a vendor to change a setting.
What this rules in:
Every setting, every credential, every template, every routing rule, every feature toggle, every custom field, every taxonomy entry, every role definition, every permission grant — all of it has a UI
screen behind the	permission.
Every integration (SMS provider, email server, AI provider, Omni channel APIs, payment gateway, etc.) is registered, credential-managed, tested, enabled, and disabled from the UI.

Schema extension (Custom Fields on Cases / Tax Payers / Organizations / etc.) happens at runtime via the Custom Fields admin screen — no database migration needed for a new field.
Notification message text (email subjects/bodies, SMS bodies, in-app messages) is editable from the UI — no code changes to reword a sentence.
Workflow stages can be enabled, disabled, reordered, or reconfigured from the Case Workflow settings screen — no code changes to alter the pipeline.
Roles can be created, cloned, modified, deleted, and per-user-overridden — no code changes to introduce a new role.
Cache invalidation, permission refresh, maintenance-mode toggle — all UI controls.
Module install / update / uninstall — UI-driven via Module Marketplace.
Branding (logo, primary color, footer text) — UI-uploaded; no asset redeploy.

What this means for the dev team:
Every time you reach for a config file, ask: does the Super Admin need to be able to change this without me? If yes, build the admin UI.
Every time you introduce a new entity field, ask: does this need a migration or can it be a Custom Field? If it can be a Custom Field, prefer Custom Field.
Every time you hardcode a string that a user might want to change (notification text, error message, button label), ask: does the admin need to edit this? If yes, put it in an editable strings table.
Every time you wire an integration, build the credentials UI first, the test-connection button second, and the actual integration call third.
Acceptance principle (AC-2.3): The Platform MUST pass a "Super Admin only" operational drill in which a Super Admin user, with no engineer present and no shell access, can perform every routine administrative task: add a new department, add a new service domain, change the IMAP host for the complaints mailbox, change the email template for "case forwarded to next stage", reset a user's password, grant a new permission override, install a new module, change the logo, enable / disable a feature flag, and view the audit trail of all the above.
