1. Executive summary

The Tax Ombud Operations Platform is an integrated CRM + ERP + ITSM (Information Technology

Service Management) system built for the Office of the Tax Ombud (OTO) of the Federal Republic of

Nigeria. It serves three audiences from a single backend through three distinct front-ends:

1. The public — Nigerian taxpayers lodging and tracking complaints against tax authorities.

2. OTO staff — case officers, supervisors, approvers, executives, and corporate-services staff who

triage, investigate, and resolve those complaints, and who run OTO's internal HR, payroll, IT, and

procurement operations.

3. OTO administrators — sitewide configuration, role governance, integrations, audit, super-admin

controls.

The Platform's core job is to receive, manage, route, escalate, approve, and resolve complaints against

tax authorities (NRS, NCS, state IRS, LGRC, NPA, AMCON, NSC, and others), then forward them to the

appropriate handling authority while preserving an unbroken audit trail. Around that core, it provides the

full operational fabric an independent government office needs to run: HR, payroll, leave, attendance,

performance, internal tickets, projects, inventory, secured document filing with OCR, e-voting, e-

signatures, omnichannel taxpayer communication, knowledge management, automation/workflow rules,

and reporting.

Scale of the build:

19 functional sections, 119 topics (modules/pages), 205 distinct permission grants

Three front-end experiences (public portal, taxpayer portal, staff studio) sharing one backend

Multi-stage configurable workflow with 5 confirmed officer queues (Receiving → Verifier →

Assessment → Investigation/Resolution → 1st Level Approval → 2nd Level Approval)

Multi-channel omnichannel inbox (Chat, Email, Calls, SMS, WhatsApp, Facebook, Instagram,

Telegram, X/Twitter)

Audit-grade governance including admin impersonation with full traceability

NDPR-aligned data handling for Nigerian PII (NIN, BVN, taxpayer financial data)

Primary success metrics for the build:

Median complaint intake-to-acknowledgement time ≤ 1 business day

≥ 70% of complaints resolved at Assessment Officer (B1) stage without further escalation

[ASSUMPTION: KB suggests "Typically 70–80% of cases should resolve at B1"]

100% of state transitions audited and recoverable

99.5% uptime for the public portal lodging flow [ASSUMPTION: standard gov SLO]

Zero PII leakage incidents

Non-negotiable foundational principle (see §2.3): The Platform is self-administered from the UI by

the Super Admin role. Every operational adjustment — new departments, new service domains, new

roles, new permission grants, new email templates, new feature toggles, new integration credentials,

2. Product context and goals

2.1 Who OTO is, who they serve, what hurts today

The Office of the Tax Ombud is constituted as an impartial mediator between Nigerian taxpayers and

tax authorities. Its tagline on the public portal is "An Independent Office for Fair and Transparent Tax

Administration." When a taxpayer (individual, SME, or large corporation) has a grievance against a tax

authority — disputed assessment, unresolved VAT remittance, alleged poor service at an MSTO office,

refusal to process refunds, etc. — OTO is the recourse channel.

Today, without a system like the Platform, OTO faces these operational problems:

Fragmented intake: complaints arrive by email, phone, social media, in-person visits, and physical

letters. No single record.

Untraceable handoffs: cases move between officers and departments without an audit trail.

No SLA enforcement: a taxpayer's complaint can sit untouched for weeks.

Manual forwarding to authorities: officers manually email/letter the NRS/NCS/etc. with no status

sync.

No reporting: leadership cannot answer "how many VAT-related complaints did we receive this

quarter, and how many did we resolve at Assessment vs. escalation?"

Internal operations on spreadsheets: HR, payroll, leave, IT tickets, procurement all run on

disconnected tools.

The Platform solves these by giving OTO a single system covering both the outward-facing complaint

mediation function and the inward-facing organisational operations

(HR/Payroll/IT/Finance/Procurement) needed to run an independent statutory office.

2.3 Foundational principle — the Platform is self-administered from the UI

This is a non-negotiable architectural constraint that shapes every other decision in this PRD.

The live system being cloned was deliberately built so that a Super Admin user, signed into the staff

studio, can manage and administer every aspect of the application from the UI alone. There is no

scenario in normal operations where an administrator must SSH into a server, edit a configuration file,

run a database migration, redeploy code, or call a vendor to change a setting.

What this rules in:

Every setting, every credential, every template, every routing rule, every feature toggle, every

custom field, every taxonomy entry, every role definition, every permission grant — all of it has a UI
screen behind the  super.admin  permission.

Every integration (SMS provider, email server, AI provider, Omni channel APIs, payment gateway,

etc.) is registered, credential-managed, tested, enabled, and disabled from the UI.

Schema extension (Custom Fields on Cases / Tax Payers / Organizations / etc.) happens at runtime

via the Custom Fields admin screen — no database migration needed for a new field.

Notification message text (email subjects/bodies, SMS bodies, in-app messages) is editable from

Workflow stages can be enabled, disabled, reordered, or reconfigured from the Case Workflow

Roles can be created, cloned, modified, deleted, and per-user-overridden — no code changes to

introduce a new role.

Cache invalidation, permission refresh, maintenance-mode toggle — all UI controls.

Module install / update / uninstall — UI-driven via Module Marketplace.

Branding (logo, primary color, footer text) — UI-uploaded; no asset redeploy.

What this rules out:

❌  "Edit  conﬁg/app.php  and restart the server" — not allowed.

❌  "Run  php artisan migrate  to add a new field to the Case" — not allowed (use Custom
Fields).

❌  "Update the  .env  file with the new SMS API key" — not allowed (use System Integrations).

❌  "Modify the Liquid template file to change the notification subject" — not allowed (use

Notification Templates).

❌  "Ship a new build to introduce a new Service Domain" — not allowed (use Data Lists → Service

Domains).

❌  "Open a database client to fix a misspelled department name" — not allowed (use Departments

admin).

What this constrains in the build:

Configuration storage: Settings live in the database (one or more  settings  tables, or a
dedicated config service backed by DB). Settings tables are seeded at install but mutable

thereafter.

Schema design: Use JSONB columns on  Case ,  TaxPayer ,  Organization ,  Account ,
User ,  Ticket , and similar entities to host runtime-defined Custom Fields. The Custom Fields
admin screen writes a  custom_ﬁeld_deﬁnition  row; the user-facing forms read it to render
inputs; persisted values live in the entity's JSONB column.

Templates: All notification templates (email subject + body, SMS body, in-app message) are stored

as DB rows with the templating expression (Liquid / Handlebars). The render engine pulls from DB

at send time. NO file-system templates.

Feature flags: A DB-backed flag table read by the application on each request (with brief in-

memory cache, invalidatable via the Super Admin Feature Flags screen). NOT env-var-driven.

Credentials: All third-party credentials (SMTP password, SMS API key, Omni channel tokens, AI
provider keys, BPA secret) stored encrypted in the  integration_credentials  table, written via
the Super Admin screens, read by the integration layer. NEVER in  .env . NEVER in source.

Cache control: Every cached layer (role/permission cache, dashboard data, settings cache) has a

UI invalidation control. Per-user "Refresh Permissions" button is one example; Maintenance screen

What this means for the dev team:

Every time you reach for a config file, ask: does the Super Admin need to be able to change this

without me? If yes, build the admin UI.

Every time you introduce a new entity field, ask: does this need a migration or can it be a Custom

Field? If it can be a Custom Field, prefer Custom Field.

Every time you hardcode a string that a user might want to change (notification text, error

message, button label), ask: does the admin need to edit this? If yes, put it in an editable strings

table.

Every time you wire an integration, build the credentials UI first, the test-connection button

second, and the actual integration call third.

Acceptance principle (AC-2.3): The Platform MUST pass a "Super Admin only" operational drill in

which a Super Admin user, with no engineer present and no shell access, can perform every routine

administrative task: add a new department, add a new service domain, change the IMAP host for the

complaints mailbox, change the email template for "case forwarded to next stage", reset a user's

password, grant a new permission override, install a new module, change the logo, enable / disable a

feature flag, and view the audit trail of all the above.

6. Role catalog and RBAC model

6.1 Model overview

The Platform uses a role-based access control system with three layers:

1. Roles — named templates that bundle permissions. Each role has a  name  (display),  code  (slug,
e.g.  b1.agents ,  approver ,  call.center.agents ), a  scope  ( Sitewide  or  Private ),
and a list of permission grants.

2. Multiple-role assignment — a user can hold many roles simultaneously. Effective permissions =

union of all role grants.

3. User Permission Overrides — per-user additive grants beyond role membership, for one-off

cases.

The live system has a dedicated screen at  studio/settings/setting-roles.kml  for managing roles
and a separate screen at  studio/settings/setting-users.kml  for assigning roles to users and
applying overrides. A button "Refresh Permissions" on each user's profile lets an admin force a cache

invalidation when role grants have changed.

6.2 Scope semantics

Sitewide — the role's grants apply across the whole organisation.

Private — the role's grants are scoped (typically to the user's department, workflow lane, or

assigned records). [ASSUMPTION: "Private" scope is enforced by combining role grants with the

user's department / lane / ownership filters; the exact predicate is configured per role on the

Manage screen]

6.3 Seeded role catalog (production)

Roles observed in the live system, with their codes and scope. Permissions per role are listed where

visible (full mapping in Appendix B).

7.9 Case Approvals (Stage 6 — the Tax Ombud's terminal queue)

Page: /studio/approvals/ .

This is the terminal workflow stage, owned exclusively by the Tax Ombud — the statutory head and
Chief Executive of the Office of the Tax Ombud (or a Tax-Ombud-delegated  case.approveall
holder). It is the 6th and final stop in the complaint lifecycle for any case where
requires_approval_to_close = true  (the system default).

How cases arrive here:

1. Standard path — A case at B3 (1st Level Approval) is submitted for CE approval with the B3

officer's written recommendation. Case advances to Stage 6.

2. Direct close-approval request — An agent at an earlier stage (B1/B2) attempts to close a case

where  requires_approval_to_close = true . The system creates a close-request that lands in
Case Approvals for CE sign-off; the case itself remains in its current operational stage until the CE

decides.

3. Re-submission — If the CE returned a case for revision, the revised version re-enters Case

Approvals after B3 re-recommends.

The CE's actions (per case in the queue):

Approve — final sign-off. Case transitions to Closed with the CE's decision recorded. Approval

write includes:

CE's decision (Resolve / Resolve with Special Terms / Reject)

CE's decision rationale (mandatory, ≥ 100 chars)

Outcome notification dispatched to complainant

Reject — case rejected. Same write semantics with  outcome = rejected .

Return to B3 — for revision; mandatory reason; case re-enters B3 queue.

Cancel — withdraws the approval request without a decision (rare; e.g. if the case was created in

error). Case remains in its source stage.

22.5 Acceptance — what "done" looks like for MVP

The MVP (Phase 1, sprint 1–10) is shippable when:

1. A citizen can submit a complaint via the public portal, receive a reference number by email, and

track it.

2. A Receiving Officer can pick up the complaint, fill mandatory fields, and forward to Verify.

3. The case flows through Verify → B1 → B2 → B3 → Case Approvals (CE) — every stage tested.

4. The Tax Ombud (CE) can approve a case at Stage 6 with a written rationale, and the citizen

receives a closure notification.

5. Every state transition is in the audit log.

6. A Super Admin can perform the AC-2.3 operational drill: add a department, add a service domain,

change the IMAP host, change a notification template, reset a user's password, grant a permission

override, change the logo, view the audit trail — all from the UI, no shell access.

7. The deployment passes NDPR review by the OTO DPO.
